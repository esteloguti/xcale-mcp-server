## 1. What LobbyPMS is, and who is waiting

LobbyPMS is the most widespread modern PMS among Colombian hotels (1,650+ properties). Two properties
are waiting for the integration: Entrenubes Ecohotel (LobbyPMS id 339654) and Hotel Sexto (Armenia).
LobbyPMS answered both in writing on 2026-10-13/14 (the team's email thread "Integración LobbyPMS —
Entrenubes Ecohotel y Hotel Sexto", 2026-10-15).

## 2. Facts (Documented — https://app.lobbypms.com/api, read 2026-10-15)

| # | Fact |
|---|---|
| F1 | REST + JSON at `https://api.lobbypms.com/api/v1/…` (one method in `v2`). |
| F2 | **Auth: one API token per property**, generated by an ADMINISTRATOR in the property's account (Configuraciones › Usuarios, Permisos y API › Acceso API › Ver API Token), sent as `api_token` on every method. The payment-link section says "token Bearer". |
| F3 | **The caller's public IP must be authorized in the property**, one by one; no authorization by domain (LobbyPMS emails). |
| F4 | No sandbox; tests run in a client's real account. Rate limit ≈ 60 requests/minute. No webhooks. |
| F5 | **No endpoint lists bookings or guests, and none modifies a booking** (emails + the method list). |
| F6 | `GET v1/available-rooms` / `v2/available-rooms` (`start_date`, `end_date`, optional `category_id`, `page`, `paginate` ≤ 50): per date, per category, `available_rooms`, prices **per number of people** (`[{ people, value }]`) and `restrictions { min_stay, max_stay, lead_days }`. v2 groups prices by rate plan (`plans[]`, the standard one is `STANDARD_RATE`, `id: null`). No currency in the payload. |
| F7 | `POST v1/bookings`: one `category_id`, dates, `total_adults` (+ `total_children`), holder by `holder_name` or by `customer_document` + `customer_nationality`, optional `rates_per_day`, `note`, `payment`, `channel`. Returns `data: [{ idBooking, idRoom }]` — an array. |
| F8 | `GET v1/bookings/{id}`: Spanish field names, status `estatus`, dates as `YYYY-MM-DD 05:00:00`, `tarifas_por_dia`, `impuesto_alojamiento` (e.g. IVA 19 %), `grupo` (sibling bookings), `deleted_at`. |
| F9 | `POST v1/cancel-booking/{id}` with a `cancellation_reason` code (NS, RC, RE, TTC, CC, OTH). Refusals carry `error_code`: `RECORD_NOT_FOUND`, **`UNAUTHORIZED_BOOKING` (not created by the API)**, `BOOKING_CHECK_IN_COMPLETE`, `RESTRICTED_RESERVATION` (payments or extra charges). |
| F10 | `POST v1/block` holds rooms of a category for `time` minutes (default 60); `DELETE v1/block/{id}` releases it. |
| F11 | Payment links (`/v1/payment/link`): created in the property's own payment system, amount ≥ 6 and ≤ the outstanding balance, one OPEN link per booking, expiry ≤ 12 months (default 24 h). Returns `currency` and `url`. |
| F12 | `POST v1/customer/{1|2}` (person / company) returns `{ status: "success" }` — no id. |

## 2b. Observed (anonymous probes, 2026-10-15, from a non-authorized IP, no valid token)

| # | Observation |
|---|---|
| E1 | `GET v1/rooms` with no token, `?api_token=<invalid>`, `Authorization: Bearer <invalid>`, and `POST v1/block` with the invalid token in the JSON body: all **`401`, `{"error":"Unauthenticated."}`**, `Content-Type: application/json`, behind Cloudflare. `GET v1/bookings/1` the same — the token is checked before the route. |
| E2 | CORS `access-control-allow-headers` lists `Authorization` and `X-Auth-Token` — consistent with a Bearer guard (Q1), not yet proven with a valid token. |
| E3 | No rate-limit headers on a 401. |
| E4 | The provider itself, run live through `scripts/lobbypms-live-probe.ts` with a fake token: all seven reads reach LobbyPMS (130–690 ms) and come back `PROVIDER_AUTH_EXPIRED` with `LobbyPMS <verb> failed (HTTP 401)`; the token appears in no output and no saved file. |

So a bad token is a 401 with a JSON body and no `error_code`, which maps to `PROVIDER_AUTH_EXPIRED` (reconnect) — the right answer for it. Still open (Q2): what a VALID token returns from an IP the property has not authorized.

## 3. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | `api_key`, one field `api_token`, **query placement**, `forwarded`. | F2: the only placement documented for every method. Forwarded like Cloudbeds (a booking PMS); payment links are the property's own system, this server moves no money. Token-in-URL containment tests, as Toteat. **Switch to `bearer` if Q1 shows it works everywhere.** |
| D2 | Context `propertyId` (required, never sent to LobbyPMS). | The token selects the property and the URLs name none (F2), but a consumer must tell two properties apart without keying on a secret. The LobbyPMS property id is that identity. |
| D3 | `connectionProbe` = `list_room_types`. | Cheap, no arguments, money-free — and it proves token, API access **and** the IP authorization (F3) in one call. |
| D4 | Agent menu = `list_room_types` + `check_availability` (prices **stripped**, a documented projection). Everything else `controlPlane`. | The money guard: prices, guest data and writes are composed and gated by the consumer. |
| D5 | One narrow error override: a body naming a documented business code (F9, `INPUT_PARAMETERS`) is never `PROVIDER_AUTH_EXPIRED`; its machine code goes in the message. A 401/403 without one keeps the core map. | `UNAUTHORIZED_BOOKING` on a 401 would flip a working connection to "reconnect". Free text is never forwarded. |
| D6 | No tool for rooms/status, occupancy, daily-occupancy, products, add-product-service. | Curated: no consumer flow needs them yet. |
| D7 | Dedicated egress IPs on the App Platform app (`.do/app.yaml` › `egress: DEDICATED_IP`). | F3. Two static IPs that survive redeploys (US$25/month). Every call of this server leaves from them, so each property authorizes the same two IPs once. **A spec applied without the block releases them for good.** |

## 4. Open questions — closed by the first read-only session

**How:** with a property's token and this machine's IP authorized in the property,
`LOBBYPMS_API_TOKEN=… npx tsx scripts/lobbypms-live-probe.ts --property <id>` — read-only, through the
provider's own code, responses saved for review. Run it once more from an IP the property has NOT
authorized to close Q2.

Probes that touch no guest data and create nothing: `list_room_types`, `check_availability` and
`get_availability_rates` on a future window, `get_booking` with an id that cannot exist, `list_channels`,
`list_document_types`, `list_rate_plans`.

| # | Question | Why it matters |
|---|---|---|
| Q1 | Does `Authorization: Bearer` work on every method? Does `api_token` in the query work on the POST methods? | D1's placement. |
| Q2 | What does a call from an unauthorized IP return — status and body? And a bad token? | If the IP refusal is a 401/403 it maps to "reconnect", and the owner would re-paste a good token instead of authorizing the IP. Narrow the override only on that evidence. |
| Q3 | Are the prices tax-inclusive? (F8 shows a separate IVA line.) In what currency? | The consumer's quote must never present a net price as the total. |
| Q4 | If `create_booking` omits `rates_per_day`, does LobbyPMS price the stay itself, at the same value the availability read showed? | Whether the consumer sends the prices it quoted. |
| Q5 | Does `create_booking` with `total_adults` above one room's capacity return several `{ idBooking, idRoom }`? | F7 returns an array. |
| Q6 | Does `get_booking` return the `note` we stamp (`nota`)? | It is the only place an idempotency reference can travel; there is no search by it (F5). |
| Q7 | Real error statuses (422 vs 400) and the shape of a 429. | Error mapping is documented, not observed. |
| Q8 | Is there an undocumented way to list bookings changed since a date? | Without one, reservations made outside the agent cannot reach the CRM (F5) — #1612. Ask integrations@lobbypms.com. |

No booking, customer, block or payment link is created in a property's account without Esteban's
go-ahead (his request, 2026-10-15).
